# 本地翻译质量 Harness 可行性研究

日期：2026-10-18。范围：以本项目现有本地 2B 翻译链路为起点，探索语义准确与专业中文表达的共同提升。

**结论：可行，但应先建设可复现的评估 Harness，再决定生产流水线。最值得验证的是“段落语境＋有出处的词义与术语记录＋少量受控修订”；不能把增加提示词、多轮反思或多个角色当成质量保证。**

本文依据项目源码和下列原始论文、官方文档制定方案。尚未对本机模型运行新流水线，也未测得质量、耗时或显存提升。配套挑战集是诊断材料，不是独立测试集；本文不修改生产代码、不下载模型、不启动推理服务。

外部研究工具的原始检索报告另存为 `translation-quality-research-raw-2026-10-18.json`，其中包含自动综合与二手来源，未直接作为已证实结论；本报告的技术依据以实际核对的原始论文和官方资料为准。

## 1. 现有问题与目标拆分

| 观察 | 错误性质 | 需要的能力 |
| --- | --- | --- |
| stakes → 赌局风险 | 习语被按常见字面义解释，加入赌博场景 | 语境消歧、禁止补入无依据的情境 |
| corporation → 该公司／企业，而上下文包含行会与宗教组织 | 词义和指称范围误判 | 段落层面消歧、按语境选词 |
| ventures → 创业活动 | 商业词义误用 | 同一语境内的关联词义检查 |
| within reach → 成就之前 | 时间范围被扩大 | 限定条件、范围与时间关系保护 |
| will → 可能会 | 新增不确定性 | 情态与判断强度保护 |
| majority sufficiency → 多数意见的充分性 | 字面上对应，中文关系不清 | 将抽象名词结构改写为自然关系表达 |
| patron 关系被流畅改写省略 | 漏译 | 命题与关系覆盖检查 |

“忠实”和“自然”应分别评价。词义错误不是靠更华丽的文风修复；术语统一也不能把一个错误译法统一到底。不得将 corporation→法人团体写成跨所有文本的全局替换规则，现代商业段落中“公司”完全可能正确。

## 2. 研究证据及其边界

1. [TEaR](https://arxiv.org/abs/2402.16379)研究翻译、估错、修订流程，报告了质量改善，并指出估错策略影响最终修订。它支持测试可验证的反馈机制，不证明当前 2B 模型能胜任双语审校。
2. [Iterative Translation Refinement](https://arxiv.org/abs/2306.03856)强调修订需锚定原文与初稿，并发现字符串指标与自然度评价可能不一致。
3. [ACL 2026 的文学翻译修订研究](https://aclanthology.org/2026.acl-long.268/)在其六个模型、七个语言对的实验中发现，文档翻译后分段修订较稳定；简单通用修订优于若干复杂估错后修订方法，收益主要来自流畅度，语义充分性改善有限。这是必须保留“简单二次修订”对照组的原因，不能预设复杂审校胜出。
4. [DiBiMT](https://aclanthology.org/2022.acl-long.298/)专门测量机器翻译的词义偏差，说明通用总分不足以解释本项目的 corporation 一类错误。
5. [xCOMET](https://aclanthology.org/2024.tacl-1.54/)可预测错误片段及严重程度；[COMET 官方实现](https://github.com/Unbabel/COMET)提供参考译文与无参考评估、候选排序等能力。但评估模型不等于事实裁判，额外模型也有内存、依赖和权重许可成本，适合先用于离线研究。
6. [MBR 指标偏差研究](https://aclanthology.org/2024.wmt-1.109/)发现，神经指标会高估按指标选出的译文，甚至换一个神经指标仍有偏差。不能用同一个评分器既优化输出又宣布成功。
7. [Experts, Errors, and Context](https://aclanthology.org/2021.tacl-1.87/)支持让专业译者结合文档上下文进行 MQM 错误标注，而不只由普通读者评价流畅程度。
8. [Index-Translate 官方项目](https://github.com/bilibili/Index-Translate)提供术语、格式、风格与领域消歧约束；目前也列出更大模型。现有项目注册表仍只接入三个 2B 模型，因此“更大模型对照”是研究选项，不是已具备的产品功能。
9. [词义消歧辅助 LLM 翻译研究](https://aclanthology.org/2025.loreslm-1.10/)探索向提示词提供词义，以及先用源语言模型预测词义再提供给翻译模型，支持单独研究词义信号。[RAGtrans](https://aclanthology.org/2025.findings-emnlp.313/)研究检索非结构化文档，并配合训练提高利用资料的能力；不能把其训练后收益理解为给任何现成 2B 模型附上资料就会自动获得相同收益。

以上研究跨任务、模型和语言，不可把其论文收益百分比直接移用于本项目。

## 3. 两个 Harness：评估与运行分开

### 3.1 评估 Harness：优先建设

职责是固定输入与条件、执行多个方案、保存各阶段结果、制作匿名对照、统计质量与成本。它不负责自动宣布哪一版正确。

每次运行记录：

- 模型仓库与 revision、GGUF 文件哈希、量化、服务端版本和 chat template。
- 完整提示词哈希、领域与术语记录版本、上下文窗口、采样参数和种子。
- 输入/输出 token、首次可见输出耗时、最终结果耗时、峰值显存/内存、模型切换耗时。
- 初稿、改稿、改动位置、规则检查、审校意见及是否被采纳；失败和弃权都保留。

输入给模型的内容只包含原文、允许的上下文和实际可用的术语资料。参考译文、检查点、gold 标签和评委意见均留在评估端，避免答案泄漏。

配套 `translation-quality-pilot-cases.json` 提供 12 组原创最小对照、共 24 条诊断输入。其中 `checks` 和 `reviewer_notes` 不能进入生成提示词。该文件没有唯一参考译文，检查的是语义差别。

### 3.2 运行 Harness：经评估后再接入

```text
保守输入整理＋保留源位置映射
            ↓
邻近原文／文档简报＋检索到的已确认术语
            ↓
初译 → 确定性检查＋风险分流
            ├─ 低风险：交付初稿
            └─ 高风险：带原文的审校／一次修订
                              ↓
                       复核候选与初稿
                       ├─ 有支持：采用候选
                       └─ 不确定：保留候选与疑点，必要时请用户确认
```

这个图是待验证设计。纯 2B 模式不应假装拥有一个可靠的独立审校专家；能力探测不通过时，关闭该分支，而不是强迫模型输出看似专业的 JSON。

## 4. 推荐算法细节

### 4.1 先解决输入质量与语境，而非先加调用轮数

保留段落、标题、前后文和原文，不把整篇切成互不关联的句子。采用“输出目标段落、邻近原文只供参考”的窗口；上下文长度在开发集上选择，不预设越长越好。

阅读器/PDF 常见的 `institu-\ntions` 可在确认属于断行连字符时恢复。但 `long-\nterm`、代码和路径不能盲目合并。先处理明确的软连字符；不确定的普通连字符借助本地词表或保持原样，并维护原始文本与规范化文本的双向偏移映射。

文档简报只保存文体、时空背景、核心指称和已确认术语；摘要不能替代原文证据。摘要错误会污染后续所有段落，因此自动简报是可撤销的建议，不是新的事实来源。

### 4.2 词义与术语记录应有作用域和出处

```json
{
  "source_term": "corporation",
  "sense_id": "historical_corporate_body",
  "domain": "欧洲制度史",
  "scope_id": "document_or_chapter_id",
  "target": "法人团体",
  "evidence_quote": "guilds, city charters, religious organizations",
  "origin": "translator_confirmed",
  "status": "confirmed"
}
```

这是记录格式示例，不是全局词典条目。先检索用户确认过的同文档、同领域记录，再提供少量相关译例。初期可用本地精确/关键词检索，不必先部署向量数据库。

自动提出的词义先标为 `proposed`，不能自动写回永久术语本；文档切换、作者换义或出现反证时允许失效。上下文中的例子只用于判断词义，不将其中的事实补入译文。

### 4.3 风险检测须区分可验证规则与模型判断

| 检查 | 可做到的事 | 不应声称做到的事 |
| --- | --- | --- |
| 数值、版本、代码、占位符、结构 | 检查已保护对象是否丢失或变形 | 仅凭正则判断所有数字语义正确 |
| 数量规范化 | 在支持的语言/表达中对齐 twelve、12、十二 | 把不同写法一律当错，或自动换算所有单位 |
| 情态、否定、比较、因果、时间词 | 找出需要重点审校的原文片段 | 仅靠词表证明整句语义等价 |
| 段落缺失、重复、结束原因 | 发现疑似截断、漏段、重复输出 | 用长度比判断译文忠实程度 |
| 词义冲突与审校模型 | 提出带原文出处的疑点 | 直接把模型自报置信度当成正确概率 |

数字检查需识别百分比与百分点，允许合法目标语表达变化。对齐不确定时记录疑点，不直接篡改内容。风险触发规则和评分阈值在开发集校准，报告误报率与漏报率。

### 4.4 审校结果必须具体、可核对，并允许没有问题

审校输入始终包含原文、必要原文上下文和初译。输出最多若干项问题：

```json
{
  "issues": [{
    "type": "meaning_or_scope",
    "severity": "major",
    "source_quote": "within reach",
    "target_quote": "在成就伟业之前",
    "reason": "原文限定为已可企及，而译文覆盖所有此前时间",
    "suggested_change": "已近在眼前"
  }],
  "abstain": false
}
```

代码检查引文是否确实出现在相应文本中；这只能证明引用没有捏造，不能证明解释正确。严重程度仍是待验证判断。允许 `issues: []` 或 `abstain: true`，不要要求每段必须找出若干错误。

先以已注入已知错误的中英片段测审校能力，包括误改正确译文的概率，再决定是否启用。若翻译专用 2B 不服从审校任务，保留翻译职责；可选的本地通用审校模型需另行评测，而不是给同一个模型换角色名。

### 4.5 修语义与修文风分开评估，修订次数有上限

候选 1 是带原文的简单通用修订；候选 2 才是利用具体已验证疑点的修订。两者都必须在实验中比较，不能预先指定复杂方案为优胜。

语义修订只处理有依据的问题，保留其余内容；文风修订允许拆句、调整信息顺序和把名词结构改为自然中文，但保持指称、数量、情态、因果、评价强度。不能把先前模型提取的“语义清单”当作完整真值，原文始终是最终参照。

第一阶段最多一次候选修订，必要的复核之后停止。不要默认运行“翻译→批评→改写”五轮循环。所有候选保留初稿，出现新的可验证错误时回退；初稿本身有未解决的严重疑点时，应显示待复核，而非宣称回退就安全。

### 4.6 候选选择采用分层条件，不用文风抵消误译

建议原则：先排除违反明确硬约束或产生新数字/结构错误的候选；再比较语义与覆盖；最后在语义相当时比较自然度。复杂语义是否相当仍有不确定性，不能由一项规则检查“认证”。

两个候选意见一致不代表词义正确——它们可能都把 corporation 译成企业。大规模 MBR 与多数票不适合作为首个版本；先比较 2–3 个有差异的候选，并用独立评价验证排序是否可靠。当前主翻译温度为 0，重复同样请求通常缺少有效差异；若试采样，参数变化和候选数必须单独计入实验。

反向翻译只可提供辅助疑点。正反向模型可能以一致方式犯错，也可能把错误译文“修复”成貌似正确的原文，因此不能作为忠实度验收条件。

## 5. 与当前代码的衔接

| 当前入口 | 可复用内容 | 接入前需要解决的问题 |
| --- | --- | --- |
| `app/internal/translator/translator.go` | Translate、TranslateSync、TranslateRawSync、上下文取消 | 加独立 QualityRunner，先不改动官方默认提示词 |
| `app/internal/translator/sse.go` | 本地兼容接口、流式事件、用量与结束原因字段 | 结果向上保留截断信息；增加并实测结构化响应配置 |
| `app/internal/translator/prompt_translate.go` | 已有术语与硬/软约束 | 注入作用域内证据，区分原文、参考上下文和任务指令 |
| `app/internal/docpipeline/pipeline.go` | 分块、取消、断点与失败处理 | 补充跨块原文和术语状态；当前块级重试针对调用失败，不等于质量纠错 |
| `app/internal/orchestrator/orchestrator.go` | 任务计数、单模型生命周期和释放机制 | 整条质量流程保持一个父任务；模型切换期间正确清理/恢复任务与取消状态 |
| `frontend/src/lib/modes.ts` | 领域预设 | 领域与处理深度分开：如“人文写作＋审校”，不要再增加十几个混合预设 |

当前预算以源文估算并预留固定模板余量，多阶段提示词包含原文、初译、上下文和意见后，不再适用。应计算渲染后的完整 chat prompt，预留输出和误差；优先削减参考上下文与译例，不截去待译原文。[llama.cpp 官方服务文档](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md)提供 `/apply-template`、`/tokenize` 与结构化响应能力，但项目所带服务端是否支持及具体参数形式必须实测；JSON 语法受限不等于内容正确。

建议接口草案：

```text
QualityRequest {
  source, sourceContext, documentID, targetLanguage,
  domainPreset, qualityPolicy, confirmedTerminology
}
QualityResult {
  draft, final, stage, candidates,
  suspectedIssues, deterministicChecks,
  needsReview, finishReason, usage
}
```

流式显示初稿时明确“初译”，校对完成后再提交最终稿。校对中取消保留已有初稿，不能让它假装是已审定最终稿。历史记录只提交最终选择，初稿和意见仅在本地实验运行中由用户显式选择保存；正式产品沿用默认不记录日志的设置，不把原文或审校文本写入应用/引擎日志。

## 6. 方案比较与成本

| 方案 | 主要收益假设 | 成本与风险 | 建议 |
| --- | --- | --- | --- |
| 更长的通用提示词 | 强化已知规则 | 约束竞争，无法补足词义知识 | 保留现有预设作基线 |
| 语境＋已确认术语检索 | 改善词义与一致性 | 错误记忆会扩散，增加输入长度 | 最先试 |
| 同一 2B 二次修订 | 可能改善中文表达 | 同源盲点，可能误改正确内容 | 必须设对照，最多一次 |
| 风险触发局部修订 | 把计算集中在疑难段落 | 触发器漏检、错误审校 | 先离线校准 |
| 本地更强模型审校/重译 | 引入新的理解能力 | 权重、KV cache、切换与延迟；模型也会错 | 可选研究分支 |
| 更大模型单次翻译 | 更简单的产品链路 | 需要额外硬件与注册表接入 | 必须作为竞争基线 |
| 多候选＋QE/MBR | 可能选出更好表达 | 多次生成、评估模型与指标偏差 | 后期再考虑 |
| 人工译后编辑样本微调/蒸馏 | 固化特定领域改进 | 数据、许可、训练与回归维护 | 积累足量真实编辑后再试 |

不先估计固定倍数或具体秒数。若 D 是初译成本、V 是审校成本、R 是修订、P 是文风处理成本，平均时延近似 D + V + pR + qP，再加预处理、预填充和模型装卸；p、q 从实测触发率取得。不要忽略审校阶段重复输入原文与初稿的预填充开销。

串行复用同一模型通常不需要同时加载多份权重，但较长提示词会增加 KV cache。参数量×位数÷8 仅是权重理论下界，不能作为显存需求；还应计入量化元数据、KV、激活与运行开销。当前注册表的模型文件体积也不是显存实测值。尚未确认本机硬件，故不宣称某一 7B/9B 模型一定可运行。

外部资料检索与在线模型均不作为产品默认依赖，原文不自动出本机。研究期间的联网查询只讨论通用技术，不上传用户原文。

## 7. 最小实验设计与停止条件

### 7.1 消融矩阵

| 组 | 模型与流程 | 目的 |
| --- | --- | --- |
| S0 | 当前 Q4＋官方默认 | 产品基线 |
| S1 | 当前 Q4＋通用增强 | 分离已改提示词的效果 |
| S2 | 同模型 Q8＋S1（可用时） | 单独检查量化影响，不预设有提升 |
| S3 | S1＋带原文的简单二次修订 | 检查最小修订收益 |
| S4 | S1＋段落语境＋已确认术语记录 | 检查证据与记忆收益 |
| S5 | S4＋风险触发审校与一次修订 | 检查复杂流程的净收益 |
| S6 | S4＋独立的更强本地审校模型（可选） | 检查审校能力瓶颈 |
| S7 | 更大本地翻译模型单次生成（可选） | 比较流程优化与模型升级 |

S3 和 S5 均保留可选修订“不改动”的结果。S5 的审校意见不能提供给 S3，gold 译名不得注入 S4；术语记录只能来自部署时真实可用的文档信息或独立开发资料。

### 7.2 数据与人工评价

先用本次 24 条最小对照和已有评估材料排查接线，再另建约 30 段开发集、120 段未见测试集，覆盖历史社科、科普统计、技术、叙事、对话及通用文本，并加入连续文档。数量是初步计划，不代表足以证明罕见严重错误已消失。

本次对话的 corporation、stakes、within reach 已参与设计，只能算诊断或开发材料，不能算无泄漏测试。按文档划分开发/测试，不把同一文章的相邻段分到两边；最小对照的两个成员保持同一划分。

让两名能读原文的中英译者匿名、随机顺序、保留完整文档语境评审，分歧再裁决。分别记录 Accuracy、Omission/Addition、Terminology、Fluency、Style、Document consistency，使用 critical/major/minor 标签；先报告各类错误数，再提供声明权重的辅助汇总分。

自然度只在语义质量相当的候选之间比较，并保留平局。阅读器 Pro 可作匿名外部产品对照，不当金标准；其版本、设置和输出来源需记录。COMET 等指标只作辅助，并确保参考/无参考模型、语言覆盖及版本使用正确。

### 7.3 决策指标

- 严重语义错误、漏译和增译是否下降，已有正确译文是否被误改；报告每千源词错误数和文档级配对置信区间。
- 审校器的错误识别精度、漏检率、错误意见被采纳率；低质量意见会让系统负收益。
- 在语义不变条件下，译者是否偏好改稿，是否减少人工编辑时间；不能只统计“更好听”。
- p50/p95 最终时延、总 token、峰值内存/显存、取消成功率、原文与代码保护是否回归。
- 按文档做配对 bootstrap；不要把同文档多段或同义改写当作完全独立样本。

**决策规则：只有在独立测试上体现语义收益或在语义不退步时体现可靠自然度收益，且成本可接受，才接入生产。** 如果 S5 不优于 S3/S4，删除复杂阶段；如果 S7 更好且更快，优先扩大模型适配；若同一 2B 无法可靠审校，就不继续堆叠角色和反思轮数。

对高风险或出版级文本，保留译者终审入口。“接近专业译者”应指明领域、样本、评审方式与剩余错误，不能从几段流畅样例外推为全面达到专业水平。

## 8. 推荐落地顺序

1. 评估 Harness、独立测试数据、原文位置与完整 token 预算；此阶段不改默认翻译体验。
2. 小范围试验 S3/S4：简单修订与证据式词义/术语处理，检查是否各自改善不同维度。
3. 若仍存在可识别的语义错误，验证审校器后再做 S5/S6；为无法确认的问题提供弃权和对照。
4. 与更大模型单次翻译比较后，才确定“快速／校对／精修”产品档位及其默认值。

最有价值的原型不是五轮自动润色，而是能回答三个问题的实验系统：错在哪里、哪项处理修好了它、又造成了什么新错误。
