## 0. 先订正三处失真（含本文作者在此前对话中的一次算错）

1. **「2 万字跑不进 32K」这个说法是错的，但结论仍要分块。** 实测中文小说 **0.69–0.713 token/字**
   （§7.1），20,000 字 ≈ 14,260 输入 token + 17,860 输出 token + 模板 115 ≈ **32,235 / 32,768**——
   单发**理论上**装得下，但只有 1.6% 余量，且 8K/16K 完全不可能。此前按"≈1 字/token"估出的
   36–40K 高估了 31%。真正已经证实的硬上限是**请求路径写死的 `max_tokens=1024`**
   （`translator.go:243`）：§7.2 实测一篇 1503 字的小说就会被截成 `finish_reason=length`。
2. **`docpipeline.go:6` 的「stop_token_ids 请求扩展（translator 已就绪）」只在"字段能被序列化"的意义上成立。**
   `sse.go:44/79-80` 确实会发 `stop_token_ids`，`registry.go:74` 确实存着 `[248044,248046]`，
   但 `buildRequest` 的两个分支（`translator.go:236-247`）**都 `return requestExtra{}`**，
   没有任何生产代码把 registry 的值传进去。管道通了，水没接。
3. **`manager.go:531` 的注释「SetActive 请求 orchestrator 热切换」与函数体不符。**
   函数体只做 `SpecByID` 存在性检查 + `ActiveTasks()>0` 拒绝 + 写 `m.activeID` + `notify()`，
   **从头到尾没有触碰 orchestrator**，也不校验模型文件是否已下载。真正的切换是惰性的：
   下一次请求 → `ResolveEndpoint`（`app.go:212`）→ 发现 `modelPath` 变了 → 热重启。
4. **`app.go` 那条 `[assumption]` 显存估算式的 KV 斜率高估 9.3 倍**，害得本文初版
   误判"本机跑不了 32K"。式子用的是 **875 MiB / 8K**，实测拟合是 **93.7 MiB / 8K**（§4、§7.7）。
   它在 8K 这一点上偏差就有 +75%（本来就是从 8K/32K 两个文档数反推的），往上越偏越远：
   32K 预测 5315 MiB、实测模型自身只占 **1802 MiB**。**F-08 的验收环境不需要 ≥12GB 的卡。**
   该式与 `ctx_estimate_test.go` 已于同日按实测重标（取 120 MiB/8K 偏保守），
   并顺带修掉一个独立缺陷：`int(tokens/8192)×875` 的整除让 2K/4K 档的 KV 项恒为 0。

## 2. 核心矛盾：模型契约要求整篇一次进窗，而工程上限是 1024 token 输出

官方 Nailong 模板（四方向各 534 字节，`translator/testdata/official/nailong/`）`zh-en` 全文：

> 请将以下中文小说翻译成英语，并且严格遵循所有约束要求。
> 这是一段长篇连续文本，请完整处理全部内容，并在全文范围内保持译名和表达一致。
> 【约束要求】
> 1. 完整翻译所有内容，不要遗漏、概括、合并或添加内容。
> 2. 保持人名、地名、称谓和术语在全文中一致。
> 3. 保持原文的章节、段落和内容顺序。
> 只输出译文，不要有任何额外说明。
> 【源文】
> （在这里放入需要翻译的完整中文原文）

**这三条约束就是 F-08 的验收项本身**（三处「王妃」同名 / 不遗漏 / 章节段落顺序保持）。
也就是说"全文一致"不是我们的工程能力，是模型在**单次调用内**被要求做到的事——模板第 2 段
「这是一段长篇连续文本」预设整篇进同一个上下文。`BuildNailongPrompt` 也照此实现：
断言模板恰好 1 个占位符，然后把**完整原文**一次性插进去（`prompt_homura.go:84-102`）。

于是分块与契约直接冲突，而跨块一致性的实现数量是**零**，现成的两条路都堵着：

- 唯一的专名机制是 `Constraints.Glossary` → `【硬性要求】专名/术语对照`，
  只注入 `BuildTranslatePrompt`（`prompt_translate.go:22,93-94`）。**Nailong 模板没有术语槽位**
  （占位符数量被断言锁死为 1）。
- 字幕侧留了 `QueueOptions.GlossaryID`，注释写「M3 启用术语」，但整个 `internal/subtitle/`
  里 `Glossary` 只出现这一行（`engine.go:102`）——**声明了，没人读**。

更要命的是当前请求路径：`buildRequest` 的 default 分支写死 `max_tokens=1024`（`translator.go:243`）。
**chunk 尺寸今天由输出上限决定，而不是由 ctx 决定**——§7.2 已实测证实截断，
按膨胀比反推单次调用最多覆盖约 1147 个源文字符，2 万字 = **至少 18 次调用**，
每次重发 115 token 的模板。

但"分块必然破坏一致性"这个前提，§7.4 的代理实验**没有拿到证据**（跨块未出现互斥译名，
且整篇单发同样出现冠词变化）。所以本节说的是**风险未排除**，不是**风险已证实**。

## 3. 让「Nailong 其实跑不起来」的四个细节

1. **没有 Nailong 请求分支。** `buildRequest` 只有 `ModeDubbing` 与 `default`（`translator.go:236-247`）。
   走 default 就用 `BuildTranslatePrompt` + Translate 的采样参数（greedy、1024）——
   等于拿 A 模型的提示词喂 B 模型，且 `top_k=-1` / `seed=42` 这些 Nailong 官方参数一个都不会发。
2. **`--parallel 1` 硬编码**（`orchestrator/args.go`）+ 单进程 → 零并发。
   `modelPath` 一变即 `stopProcLocked("hot-switch")` 重载权重（`orchestrator.go:229-236`）。
   长文档是分钟级独占任务，中途改档位 / 切模型 = 整篇重来，规格里没有断点续译的说法。
3. **仓库没有 chars→tokens 估算器。** `EstimateCtxVRAM(tokens)` 收的是 token 入参，
   UI 让用户自己填 K。分块器必须自己算预算，而全仓库 `func *(chunk|splitText|segment)` 零命中。
   （`internal/vramestimate` 是反方向：token → 显存，不能拿来切块。）
4. **`-ngl` 自动判定原先不看 ctx —— 已修。** `resolveNGL` 曾另用一套
   「权重×1.1 + 固定 700 MiB」，而实测非权重开销随 ctx 线性增长（8K 326 → 64K 1052 MiB），
   于是在"剩余显存够小 ctx、不够大 ctx"的窗口里误判为够、下发 `-ngl 99` 后加载失败。
   2026-10-06 已让它与设置页共用 `internal/vramestimate`，并抽出 `decideNGL` 纯函数补了
   覆盖该窗口的测试（`args_test.go`）。**这条对 M5 尤其关键**：长文档要跑 32K/64K，
   正是旧公式失真最严重的区间。

## 4. 硬件现实：本机 4GB 卡的真实 ctx 上限（实测，非估算）

**订正：本节初版写「本机跑不到 32K」，是错的。** 那句结论来自仓库自己的线性估算式
`weights + ctx/8192×875 + 600`（原 `app.go:302-317`，`[assumption]` 档；现已重标并搬到
`internal/vramestimate`），而 §7.7 的实测证明**该式的 KV 斜率高估 9.3 倍**。

测量口径先说清，否则会踩同一个坑：**nvidia-smi 的 used 含桌面/DWM 基线**，本机上它在
800–1050 MiB 之间飘（两次运行就差 240 MiB）。所以只有 `模型自身占用 = 峰值 − 启动前基线`
才是可比量，下表全部按此口径（Nailong Q4_K_M，权重 1215 MiB，`-ngl 99 -fa on`）：

| ctx | 模型自身占用（实测） | 旧估算式 | 旧式高估 | 重标后预测 | 重标偏差 |
|---|---|---|---|---|---|
| 8K | 1541 MiB | 2690 | +75% | 1595 | +3.5% |
| 16K | 1650 | 3565 | +116% | 1715 | +3.9% |
| **32K** | **1802** | 5315 | **+195%** | 1955 | +8.5% |
| 64K | 2267 | 8815 | +289% | 2435 | +7.4% |
| 128K | 2935 | — | — | 3395 | +15.7% |

拟合式 `非权重 = 243 + 93.7×(ctx/8192)`，逐点 ±2.6%；代码取 **120 MiB/8K + 260 MiB**，
单向偏保守（高报 3–16%，绝不低报——低报会让用户选到 llama-server 起不来的档位）。

对 M5 的四条影响：

1. **F-08 的「ctx=32K」在本机可复现**，不需要 ≥12GB 的卡。模型自身只占 1802 MiB。
   估算式与 `ctx_estimate_test.go` 已于同日按实测重标（另修掉一个整除缺陷：
   `int(tokens/8192)×875` 让 2K/4K 档的 KV 项恒为 0）。
2. **真正的天花板约 131072**（模型自身 2935 MiB；加基线后 nvidia-smi 峰值 3740/4096 = 91%）。
   所以限制 M5 的是 `config` 的 2048–65536 **产品钳位**，不是显卡。
3. **大 ctx 的代价在 prefill 延迟，不在显存**：TTFT 从 8K 的 2.61s 涨到 64K 的 25.80s，
   decode 却只从 83.77 掉到 64.76 tok/s。分块策略因此应偏向**少而大的块**——
   每块都要付一次 prefill，滑窗的重叠前缀是纯浪费。
4. 用户已开启共享内存，但**本次七档全都没触到 4096 上限**。也就是说"能跑 64K"的原因是
   KV 比估算便宜 9 倍，**不是**显存溢出到了系统内存。这条必须说清，
   否则会被误读成"开了共享内存就能随便加档"。

### 7.1 中文 token 密度（`llama-tokenize.exe` 直量，三种真实文本）

| 样本 | 字符 | token | token/字 |
|---|---|---|---|
| 自撰小说正文 | 551 | 380 | **0.690** |
| `docs/01` 技术中文 | 704 | 285 | 0.405 |
| README 中英混排 | 3574 | 1964 | 0.550 |

**小说正文比技术文档密 70%**——分块器若按"1 字 ≈ 1 token"估，会**低估** 31% 的预算；
若按技术文档的 0.4 估，会高估 42%。**必须按文体分档，不能一个常数。**
Nailong 模板本体 = **115 token**（194 字 / 534 字节），每次调用都要重发。

### 7.2 `max_tokens=1024` 截断：已证实

同一篇 1503 字小说，`temperature=0`：

| 请求 | `finish_reason` | 产出 token | 用时 | tok/s |
|---|---|---|---|---|
| `max_tokens=1024`（生产现值） | **`length`** ← 被截断 | 1024 | 12.1s | 84.79 |
| `max_tokens=4096` | `stop`（正常收尾） | 1342 | 15.4s | 87.04 |

**今天这条请求路径连 1500 字的小说都吐不完整**，会在句中截断且 `finish_reason=length`——
好消息是截断可检测。按 1024 / 0.893 反推，**单次调用最多覆盖约 1147 个源文字符**，
F-08 的 2 万字 = **至少 18 次调用**。

### 7.3 中→英膨胀比与"整篇一次进窗"到底够不够

实测：输入 **0.713 token/字**（含 chat 模板开销）、输出 **0.893 token/源字**。
外推到 F-08 的 2 万字：

```
输入 20000 × 0.713 ≈ 14,260
输出 20000 × 0.893 ≈ 17,860
模板                    115
合计                ≈ 32,235  /  32,768 档
```

**余量只有约 530 token（1.6%）**——所以订正 §0.1 的说法：32K 单发**理论上**装得下 2 万字，
但零冗余（换个稍长的词表、多几个对话段就溢出），8K/16K 完全不可能。
结论仍然是**必须分块**，只是理由是"余量不可靠 + 输出上限 1024"，不是"ctx 绝对不够"。

### 7.4 分块后的术语漂移：**本次未复现**

三个 chunk（478 / 506 / 485 字）各自独立调用，与整篇一次调用对照：

| | 王妃 的译法 | 李慕 的译法 |
|---|---|---|
| chunk 0 | the princess / princess | li mu |
| chunk 1 | the princess | li mu |
| chunk 2 | the princess / princess | li mu / **li** |
| **整篇一次** | the princess / princess | li mu / **li** |

三点要诚实说明：

1. **跨块没有出现互斥译名**（没有出现 queen / consort 之类分叉），而最后一列说明
   `princess` 与 `the princess`、`li` 与 `li mu` 的差异**在整篇单次调用里同样存在**——
   它们是冠词与称呼的语法变化，不是分块造成的漂移。
2. 因此**"分块必然破坏一致性"这个假设，在本次实验里没有拿到证据**。§8.1 的成本判断要据此下调。
3. 但本次实验**不足以推翻它**：样本仅 1503 字、称谓只有两个、且模型是 Translate-2B 而非 Nailong；
   正则也无法区分语法变化与真漂移。**这条已在 §7.9（短程）与 §7.10（长程 18k 字）用真 Nailong 重做，
   结论翻转——漂移确实存在，且随跨度加剧（50% → 70%）。**
   本小节的"未复现"是样本太短 + 判定器分不清冠词变化造成的假阴性，**勿引用本表作结论**。

### 7.5 顺带量到的：ETA 完全可算

本机 8K 档稳定在 **85–87 tok/s**（预热后），1342 token 用时 15.4s。
`DocProgress` 的 ETA 用 `剩余源字 × 0.893 ÷ 85` 即可，误差主要来自 chunk 边界的空档。
注意这是 4GB 卡 + Q4 + 8K 的数，**32K 档的 tok/s 会更低**（KV 更大），别把这个数写死进代码。

### 7.6 第 3 轮的第一版又错了：`-c` 是预留，不是使用

先按"逐档启动 + 同一小样本"测了 4096…65536（`run_spike_ctx.mjs`），结果六档吞吐
几乎一模一样（80.36–80.76 tok/s），看起来"ctx 完全不要钱"。**这个结论是假的**：
样本只有 1157 token，`-c 65536` 只是把 KV 缓冲区**预留**出来，根本没被写满。
测上限必须**把上下文真填满**，于是有 `run_spike_fill.mjs`：按档位构造输入
（目标占用率 90%），并分开计 prefill 与 decode。教训写在这里，是因为
"能启动 ≠ 能用"，而 nvidia-smi 的峰值在两种测法下会给出完全不同的斜率。

同轮还暴露两个自己的缺陷，都记下来免得再犯：
`result_fill.json` 被第二次运行**覆盖**了（脚本写死了输出名，已改成 `argv[3]` 可指定），
以及构造输入时按 0.69 token/字折算没算上我加的 `【第 N 节】` 标记，
导致 2048/4096 两档被服务端以 `HTTP 400 exceed_context_size_error`（实际 2216/4318 token）拒绝。
**这个 400 反而是个有用的一手证据**：分块器估算失配时的失败模式是干净可检测的，
不会静默截断——M5 的分块预算算错了能立刻拿到明确错误。

### 7.7 Nailong 填满上下文的实测曲线（本轮主结论）

模型 `Index-Nailong-2B.Q4_K_M`（权重 1215 MiB），`-fa on --parallel 1 -ngl 99`，
`temperature=0`，固定生成 512 token，nvidia-smi 每 400ms 采样峰值。
输入 = 同一小说样本重复拼接（测容量与速率，不测质量）。
**下表「模型自身」= 峰值 − 该档启动前的桌面基线**（基线在 803–1063 MiB 间飘，必须扣）：

| `-c` | prompt tok | 填充率 | TTFT | prefill tok/s | **decode tok/s** | nvidia-smi 峰值 | **模型自身** |
|---|---|---|---|---|---|---|---|
| 8192 | 7471 | 91% | 2.61s | 2865 | **83.77** | 2346 | 1541 |
| 16384 | 14833 | 91% | 5.22s | 2841 | **80.82** | 2453 | 1650 |
| 32768 | 29561 | 90% | 11.13s | 2657 | **75.15** | 2662 | 1802 |
| 65536 | 60069 | 92% | 25.80s | 2329 | **64.76** | 3075 | 2267 |
| 81920 † | 74797 | 91% | 34.21s | 2186 | **60.15** | 3453 | 2390 |
| 98304 † | 89525 | 91% | 43.50s | 2058 | **56.62** | 3630 | 2591 |
| 131072 | 120048 | 92% | 64.33s | 1866 | **50.95** | 3740 | 2935 |

† 来自同日的另一次运行（不同桌面基线）；扣完基线后与主数据集同尺度可比，
且与拟合式的偏差只有 −0.3%～+0.2%，反过来验证了拟合。

七档全部成功启动并完成生成（`finish=length` 是因为固定只让它吐 512 token，属预期）。
拟合：**`非权重 = 243 + 93.7×(ctx/8192)`，逐点 ±2.6%**（§4 已据此重标代码常数）。

**以吞吐为基准的读法：**

- decode 从 8K 到 32K 只掉 **10.3%**（83.77→75.15），到 64K 掉 **22.7%**。
  也就是说**加大块尺寸在流速上几乎免费**。
- 真正随档位线性变贵的是 **prefill**：2.61s → 11.13s → 25.80s → 64.33s。
  每块都要付一次，所以分块数才是总时长的一阶因素，不是块大小。
- **F-08 的 2 万字在 32K 档的实测量级**：输入 14,260 + 输出 17,860 token。
  按 32K 档、每块留输出余量的保守算法约 8 块，
  总耗时 ≈ 8 × (prefill ~10s + 该块输出 ÷ 75 tok/s) ≈ **4–5 分钟**。
  `DocProgress` 的 ETA 用 `剩余源字 × 0.893 ÷ 75` 起算，再按已付 prefill 修正。
- 显存斜率 93.7 MiB/8K，与 §4 的"旧估算式高估 9.3 倍"互相印证。

### 7.8 llama.cpp 加速开关 A/B（同一 harness，ctx 32K / prompt 29561 tok）

`run_accel_bench.mjs` / `result_accel.json`。基线 = 生产 `args.go` 实际下发的组合。
判读门槛：同参数两次运行的 decode 差约 2%，**差值 <3% 一律视为噪声**。

| 配置 | prefill tok/s | decode tok/s | 模型自身显存 | 判定 |
|---|---|---|---|---|
| 基线 `-fa on` | 2673.3 | 73.80 | 1833 MiB | — |
| `-fa auto`（上游默认） | 2688.1 | 74.14 | 1791 | 与 on 等价；保留 on 明确锁定 |
| **`-fa off`** | **1912.1** | **50.41** | **2587** | **`-fa on` 值 +40%/+46%/−29%** |
| `-b 8192 -ub 2048` | 2658.6 | 72.63 | 2153 | 无收益，反多占 320 MiB → 不加 |
| `-ctk q8_0 -ctv q8_0` | 2625.8 | 68.13 | **1625** | 省 208 MiB 但 decode −7.7% → 默认不加 |
| batch↑ + KV q8_0 | 2654.3 | 68.28 | 1934 | 同上 |
| `-t 16 -tb 16` | 2640.8 | 73.48 | 1984 | 全层上卡后无差异 → 不加 |
| `-lm mlock` | 2657.4 | 72.94 | 1937 | 加载 2.0s vs 2.1s，无差异 → 不加 |

对 M5 的三条直接含义：

1. **`-fa on` 是这台机器上最划算的一个开关，绝不能为了"兼容性"关掉**——它同时改善
   prefill、decode 和显存三项。而 §7.7 的"大 ctx 主要贵在前缀填充"结论，正是在 FA 开着的前提下测的。
2. **想靠加大 batch 或 KV 量化来扩上下文，实测都没意义**：4GB 卡开 64K 已有富余，
   省下的 208 MiB 换 5.7 tok/s 不划算。真要给 ≤2GB 的机器留活路，KV q8_0 是唯一候选，
   但必须先补质量评测（本轮只看了译文开头 90 字，不足以判质量）。
3. **`--n-cpu-mem`（把 KV 放系统内存）在 vendored 的 b11406 里不存在**，
   所以"用共享内存换更大上下文"这条路当前不可用；能上 64K 靠的是 KV 本就便宜。
   Windows 侧环境：驱动 32.0.15.9186（满足 CUDA 13 构建）、电源计划高性能、
   交流供电、CPU 分发实际加载 `ggml-cpu-alderlake.dll`（i5-12500H 的正确档）。
   `HwSchMode` 注册表项未显式设置 = 走系统默认，且本次所有档位都没触到 4096 上限，
   所以共享内存是否真开启对以上结论无影响。

### 7.9 跨块一致性实测（短程 3,535 字 / 5 块，真 Nailong）—— §7.4 的加强版

`run_drift.mjs` / `result_drift.json` / `corpus_novel_zh.txt`（自撰 3535 字，12 个实体，
每个都在早/中/后段重复出现）。同一篇文稿：一次整篇调用 vs 按段落边界切成 5 块各自独立调用，
`temperature=0`、ctx 32768、其余条件全同。

判定器不用固定词典硬匹配，而是**词族正则抓表面形式 → 归一化（去冠词、弯直撇号、连字符、大小写）
→ 按"该块源文是否真有这个实体"过滤**。这三步都是踩出来的：第一轮把 `the princess` 与 `princess`
算成两种译名、把 `Chang'an` 与 `Chang’an` 算成漂移、把"源文根本没出现的尾块"算成缺失译法——
三个 bug 都会把一致误判成漂移。

**结果：6 一致 / 6 有问题。**

| 实体 | 类别 | 整篇 | 各块 | 判定 |
|---|---|---|---|---|
| 李慕 / 沈砚 / 王鹤 | 人名（音译） | Li Mu / Shen Yan / Wang He | 4 块全同形 | **一致** |
| 长安 / 江南 / 长公主 | 通名音译 | Chang'an / Jiangnan / Eldest Princess | 全同形 | **一致** |
| 青岩关 | 地名（音译 vs 意译抉择） | **Green Rock Pass** | 5 块全 **Qingyan Pass** | 整篇与分块不一致 |
| 玄甲军 | 军号 | Black-armored Army | c0/c1 Black-armored，c2/c3 **Xuanjia** | 块间漂移 |
| 太子少保 | 官职 | Crown Prince's **Young Protector** | c0 **Minister of Education**、c2 Protector、c3 整个丢掉 | **块间漂移（最严重）** |
| 楚州 | 州名 | Chuzhou | c1 Chuzhou，c2/c3/c4 **Chu Province** | 块间漂移 + 误译（州≠Province） |
| 王妃 | 称谓 | **princessess** | princessess / princess / **consort** / princess | 块间漂移 |

**两个比一致性本身更意外的发现：**

1. **模型形态缺陷**：整篇调用把 王妃 **29 次全部译成 "princessess"**（不存在的英文词，29/29），
   chunk0 同样，chunk1/chunk3 却是正确的 "the princess"。这不是分块造成的，是 Nailong
   在该上下文里的输出缺陷。**直接后果：F-08 就算一次装得下也不保证通过**，
   而"少分块就更一致"这个前提被削弱。
2. **整篇调用不是金标准**：它自己就与所有分块不一致（青岩关），且自带形态错误。
   所以 §8.1 不能拿"整篇结果"当真值去比对分块结果。

**对 §8.1 的结论（这次有数据，不是推测）：**

- 漂移**真实存在**，且**集中在"音译还是意译"的抉择类**——地名、官职、军号、称谓；
  **纯人名音译天然稳定**（4/4 块零漂移）。
- 这恰好是术语表能覆盖的范围。**选项 (c) 滑动窗口被排除**：太子少保 出现在 c0/c2/c3，
  相隔两到三块，只带上文兜不住。
- 剩下 (a) 两遍法 与 (b) 模板加术语槽，可折中：**预扫只抽"抉择类"实体**
  （地名/官职/军号/称谓），人名不抽（已稳定），把成本从"整篇重译"压到"一次短抽取 + 带表翻译"。
- **不遗漏这条本轮没问题**：每块 `输出token ÷ 源字符` = 1.029/0.953/0.961/0.981/1.176，
  整篇 0.986，五块全部 `finish=stop`，没有哪块缩水 → 未见概括或合并。
  （1.176 那个离群值是 68 字尾块，短文本固定开销所致，真实分块器会合并它。）
- **`stop_token_ids=[248044,248046]` 被本构建 b11406 接受**，探针输出正常收尾 `finish=stop`。
  M5 步 2 的前置事实成立——但生产代码至今从不填这个值（§0.2）。

**规模限制（本节不能当 F-08 结论）**：语料 3535 字 ≈ 2439 token，块间隔约 600–900 token；
F-08 要的是 2 万字、抽查点相隔 7000–14000 token。**本节测的是 1/10 跨度。**
判定器只认列出的 12 个实体，"意译掉"靠"查无"捕捉、会低估。
→ **长程复测见 §7.10**（18,292 字 / 9 块），预测"长程只会更糟"已被证实：50% → 70%。
本节另有一处需以 §7.10 为准：短程观察到的 "princessess" 29/29 形态缺陷**在长程没有复现**，
不能当作 Nailong 的稳定缺陷引用。

### 7.10 长程复测（18,292 字 / 9 块）—— 长程问题关闭，答案比短程更糟

`run_drift.mjs corpus_long_zh.txt 2000` / `result_drift.json` / `corpus_long_zh.txt`。

**不遗漏这条依然成立**：9 块 `输出token ÷ 源字符` = 0.937～1.141，整篇 0.999，
全部 `finish=stop`，没有哪块缩水。末尾两块（1.117/1.141）偏高是因为那部分是书信体，
英文展开更多——**语域会影响膨胀比**，分块预算若按小说标定，遇到公文/书信会偏紧。

**对 §8.1 的最终影响**：(c) 滑动窗口在长程下更不可能兜住；
名字表必须覆盖"复合地名 / 军号 / 官职 / 物产专名 / 描述性专名"五类，
而纯人名与著名专名（长安、江南）可以不管——它们在 9 块、18k 字跨度上零漂移。

### 7.11 0c 验证：注入名字表有效，但预扫不可行（两臂对照，生产配置）

`run_prescan.mjs` / `run_probe.mjs` / `run_drift.mjs`（`DRIFT_TABLE` + `DRIFT_OUT`），
产物 `result_prescan.json` / `result_probe.json` / `result_drift_nt.json`（臂A 无表）/
`result_drift_tbl.json`（臂B 带表）/ `glossary_test.txt`。
两臂都是**生产配置**：`chat_template_kwargs.enable_thinking=false`（同 `translator.go:132`）、
`stop_token_ids`、ctx 65536、同一语料同一分块。

**先记录两个把我带偏的混淆项**（都是自己的脚本问题，不是模型问题）：

1. 探针第一版 `max_tokens=160` 且**没关思考模式**，5 个探针全部返回空 content + `finish=length`，
   连"官方翻译任务"这个控制组也空 —— 差点得出"Nailong 不会执行模板外指令"的错误结论。
   关掉思考模式、放宽到 1024 后，控制组正常输出，探针全部有内容。
2. 预扫脚本同样漏了 `enable_thinking:false`。补上之后**结论不变**（见下），说明预扫的失败是真的。

**① 预扫召回率：长文档上完全失败。**

| 输入 | 结果 |
|---|---|
| 短文本（4 个专名的一句话） | 抽出「李慕、青岩关、王鹤、白狼河、雪」——**召回 4/4，1 个假阳性**（把"雪"当专名） |
| 只答一个词 / 列举三个词 | "H₂O" / "苹果，香蕉，梨子" —— 指令跟随正常 |
| **整篇 13,531 token 小说 + 列举指令** | **0/20 召回，模型无视指令直接开始翻译**（输出 "Chapter 1: White Wolf River…"），撞满 3000 token 上限 |

→ **Nailong 是领域微调模型，长中文输入会无条件塌回翻译任务。** 所以 §8.1 里
"(a) 预扫再过一次模型"若指"用 Nailong 通读全文"**不成立**；可行的形态只有：分块短输入抽取、
或改用通用模型（Translate-2B）、或纯规则 + 人工确认。

**② 注入有效性：机制成立，12 项入表实体的竞争译法从 8 个降到 0 个。**

| | 臂A 无表 | 臂B 带表 |
|---|---|---|
| 判定器标记有问题 | 14/20（70%） | 7/20（35%） |
| **入表的 12 个实体中，出现竞争译法的** | **8** | **0** |
| 未入表的 8 个实体中仍漂移 | 6 | 3 |

逐条看臂B 的合规情况（12 项全部命中，无一项被模型忽略）：

- **10 项逐字照表**：王妃→Queen、玄甲军→Xuanjia Army、太子少保→Junior Guardian of the Heir、
  楚州→Chu Prefecture、北境→Northern Marches、云锦→Cloud Brocade、李慕、长安、白狼河、沈三娘→Madam Shen。
- **2 项一致但被截短**：雁翅口 9 块统一输出 "Wild Goose Wing"（丢了 Pass）；
  青岩关 8/9 块 "Green Rock Pass"，末块掉成 "Green Rock"。**是截短不是竞争译法**——内部零漂移。

三个最有分量的细节：

1. **表格能逆着模型的稳定偏好改。** 王妃 在无表时 9 块一致用 "the princess"，
   入表 `王妃→Queen` 后 9 块全部改用 Queen；沈三娘 无表时稳定用 "Shen Sanniang"，
   入表 "Madam Shen" 后 8/9 块跟着换。**说明这不是"提示了模型本来就想选的那个"，而是真服从。**
2. **全新形式也能落地。** 太子少保→Junior Guardian of the Heir 与 北境→Northern Marches
   两种写法在任何无表输出里都没出现过，入表后逐字出现。
3. **顺带纠正了误译。** 楚州 无表时出现 "Chu Province"（州被译成省），
   入表 `Chu Prefecture` 后 9/9 正确。

**③ 副作用与残余问题。**

- **注入会扰动未入表的实体**：节度使 在臂A 是 9 块全 "Military Governor"（稳），
  臂B 变成 5×Governor + 1×Commissioner（漂）。**加了表反而让一个原本稳定的条目开始摇摆**，
  这提示表格的存在会改变模型对其他专名的注意力。
- **残余漂移全部集中在"表没覆盖"的实体**（节度使、铁浮图、青布）。
  所以问题从"机制有没有用"变成了"**表能不能覆盖全**"——而 ① 已经证明长文档预扫做不到。
- **成本**：注入使 prompt 增加 142 token（+1.0%），9 块合计耗时 240s→253s（**+5.4%**），
  整篇 247s→273s。可忽略。

**④ 对 §8.1 的结论**：(b')（在官方模板【约束要求】尾部追加固定译名条）**机制已被证实**，
且不需要改 `BuildNailongPrompt` 的占位符断言。真正的难点整体转移到**名字表怎么来**：
长文档预扫不可行 → 只能走"分块短输入抽取 + 合并去重 + 人工确认"，
而分块抽取本身会遇到与翻译一样的漂移（每块提出的建议译名不一致），
需要投票/多数决。**这是 M5 剩下的核心工程问题。**

## 8. 未解的设计问题（需要产品/用户拍板）
1. **一致性机制：§7.11 已经把"要不要注入"结掉了，剩下的是"表从哪来"。**
   实测：把固定译名追加到官方模板【约束要求】尾部，**12 个入表实体的竞争译法从 8 降到 0**，
   成本只有 +1.0% prompt token / +5.4% 耗时；而且表格能**逆着模型的稳定偏好改**
   （王妃 无表时 9 块一致 "the princess"，入表 Queen 后 9 块全换；沈三娘 同理），
   全新形式（Junior Guardian of the Heir、Northern Marches）也能逐字落地。
   所以 **(b') 成立**。三个选项的现状：
   - ~~(c) **滑动窗口**~~ —— **已排除**。未入表实体照样漂（节度使、铁浮图、青布），
     而且加了表还会**扰动原本稳定的条目**（节度使 从 9 块一致变成 5+1 两形）。
   - ~~(a) **两遍法：用 Nailong 通读全文做预扫**~~ —— **§7.11 ① 已证否**。
     13,531 token 的正文 + 列举指令，模型无视指令直接开始翻译（0/20 召回）。
     它只在短输入下能抽专名（4/4，带 1 个假阳性）。
   - **(b') 模板尾部追加固定译名条** —— **机制已验证**，且不动 `BuildNailongPrompt`
     的占位符断言（追加约束不新增占位符）。复用现成的 `store.Glossary` 与
     `【硬性要求】专名/术语对照` 格式（`app.go:588-609`、`prompt_translate.go:93-94`），
     缺的只是"让 Nailong 路径也读它"。
   **仍未解的三件**（这才是 0c 真正要拍的）：
   - **表的来源**：只剩三条路 —— 分块短输入抽取（但每块建议的译名本身会漂，需要投票合并）、
     改用通用模型（Translate-2B）做抽取、或纯规则 + 人工确认。
   - **覆盖率怎么度量**：残余漂移全部落在"表没覆盖"的实体上；没有覆盖率指标，
     就无法判断一次翻译的一致性是否达标。
   - **签名**：以上决定 `Pipeline.Translate` 要不要名字表入参、要不要 docID 关联
     "抽取运行"与"翻译运行"。**签名错了后面全返工。**
   **验收判据（已定，不再开放）**：不能拿整篇调用当真值（§7.10 里整篇在 青岩关、雁翅口
   上站在少数派），也不能用"表面形式是否统一"当判据（§7.10 铁浮图 一例：正则把 4 种写法
   误记成"查无"）。必须是**与批准的名字表逐条比对**。
2. **长任务的生命周期语义。** 暂停 / 取消 / 断点续译；改档位或切模型触发热重启
   （`orchestrator.go:229-236`）时已产出的部分怎么办——丢弃、保留还是续跑，规格里没说。
   另外 X 关闭时进程与显存释放本身就是未验的 UNVERIFIED 人工项。
3. **进度与 ETA 的口径。** `DocProgress` 按字符（`docpipeline.go:37-42`），模型按 token 产出。
   §7.3 给了换算依据（输出 **0.893 token/源字**），§7.7 给了速率基准（32K 档 decode 75.15 tok/s、
   prefill 2.61s/8K → 11.13s/32K）。所以 ETA 不该只有一个除法：**每块的 prefill 是固定开销**，
   漏掉它会在长任务前期严重高估剩余时间。要不要把"已生成字符"改显示成 token 口径，是产品决定。
4. **输入规模上限。** F-08 只考 2 万字，实测在 32K 档约 **4–5 分钟**跑完（§7.7），
   单线程完全可接受。要不要支持 10 万字？那会到 **20–25 分钟**量级，
   此时 `--parallel 1`（`args.go:28`）才成为真瓶颈——但开并发要改 llama-server 参数与槽位管理。
   建议 M5 先按 2 万字交付，把 10 万字明确划到范围外并写进 `docs/01`。
5. **`max_tokens` 放开到多少。** 现在写死 1024（`translator.go:243`）。M5 要么按 ctx 反推，
   要么给固定值，要么暴露成设置项。这条影响分块预算，与 1 一起定。
